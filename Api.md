# MedLab API Specification

**Document:** `API.md`  
**Product:** MedLab  
**Status:** MVP API contract  
**Primary backend:** FastAPI / Python  
**Frontend:** Next.js / TypeScript  
**Database and authentication:** Supabase PostgreSQL and Supabase Auth  
**File storage:** Private Supabase Storage  
**AI integration:** OpenRouter through a server-side provider adapter  
**Deployment:** Vercel frontend; Railway backend

## 1. API Design Philosophy & Global Conventions

### 1.1 Communication paradigm

MedLab uses a **REST-first API**. All security-sensitive operations, database mutations, medical document access, AI generation, and public share-link resolution pass through the FastAPI backend.

| Communication mechanism | MVP decision | Purpose |
|---|---|---|
| REST over HTTPS | Required | Frontend-to-backend communication |
| Supabase Auth SDK | Supported | Email and Google authentication |
| Supabase Storage SDK | Restricted | Private file upload/download using authorized, short-lived operations |
| Server Actions | Not used as a separate business API | Next.js must call the documented backend contracts |
| tRPC / GraphQL | Not used | Avoid a second API contract |
| Server-Sent Events (SSE) | Not required for the MVP | AI summaries are asynchronous operations with status polling |
| WebSockets | Not used | No real-time collaboration requirement |
| Webhooks | Only if explicitly enabled by a selected provider | No payment or subscription webhook is required for the MVP |

The API is the authoritative business-logic boundary. Frontend validation improves usability but never replaces backend authorization, validation, or database constraints.

### 1.2 Base URL and versioning

Production API base URL:

`https://<configured-api-host>/api/v1`

The actual production hostname must be configured through deployment settings; it must not be hard-coded into the application.

| Environment | Base URL |
|---|---|
| Local development | `http://localhost:8000/api/v1` |
| Production | `https://<configured-api-host>/api/v1` |

Conventions:

- Use lowercase, plural, `kebab-case` resource paths.
- Do not use trailing slashes on API routes.
- Use nouns for resource paths and HTTP methods for actions.
- Use UUIDs for resource identifiers.
- Keep versioning in the path: `/api/v1`.
- Breaking contract changes require a new API version or a coordinated migration.
- Do not expose database table names as a public contract.
- Do not expose Supabase Storage paths, token hashes, provider credentials, or raw database errors.
- The public share-link endpoint is intentionally unauthenticated but must validate the share token and its scope on every request.

### 1.3 Data formatting standards

| Concern | Contract |
|---|---|
| JSON property names | `camelCase` |
| Database column names | Exact `snake_case` names defined in `DATABASE.md` |
| UUIDs | Canonical UUID strings |
| Timestamps | ISO 8601 UTC strings, e.g. `2026-10-26T12:30:00Z` |
| Date-only values | ISO date, `YYYY-MM-DD`, for example `1995-04-12` |
| Numeric laboratory values | JSON numbers when representable without loss; clients must not round values for storage |
| File sizes | Integer bytes |
| Enums | Exact lowercase `snake_case` values from `DATABASE.md` |
| Missing optional input | Omit the field unless the contract explicitly permits `null` |
| Explicit clearing | Send `null` only for fields declared nullable and clearable |
| Response nullability | Nullable fields are returned as `null` when part of the documented response schema |
| Empty collections | Return `[]`, not `null` |
| Unknown properties | Reject on mutation requests unless the endpoint explicitly permits an extension object |

All database-facing mappings must be explicit. A public field may differ in casing from its database column, but its meaning and allowed values must not differ.

### 1.4 Standard request headers

| Header | Requirement | Meaning |
|---|---|---|
| `Authorization` | Required for authenticated backend routes | `Bearer <Supabase access token>` |
| `Content-Type` | Required for JSON request bodies | `application/json` |
| `Accept` | Recommended | `application/json` |
| `X-Request-ID` | Optional inbound; always present in responses | Client-supplied correlation ID, validated and length-limited, or generated by the backend |
| `Idempotency-Key` | Required for retryable creation/generation operations where specified | Unique client-generated key for the logical operation |
| `If-None-Match` | Optional | Reserved for future conditional retrieval; not required by MVP |
| `Origin` | Browser-dependent | Checked against configured allowed origins where applicable |

The backend must not trust a client-supplied user ID, workspace ID, role, or ownership claim. The authenticated identity comes from a verified Supabase access token.

### 1.5 Standard response headers

- `X-Request-ID`: unique request correlation identifier.
- `Cache-Control: no-store` for medical data, authentication-sensitive responses, AI summaries, and share-token responses.
- `X-Content-Type-Options: nosniff`.
- `Referrer-Policy: no-referrer` on public share-link pages and other sensitive pages.
- `Retry-After` and `X-RateLimit-Remaining` when rate-limiting applies.
- `Content-Disposition` for authorized file downloads.

Medical document responses and AI summaries must not be cached by shared proxies or public CDNs.

## 2. Standard Response Envelopes & Error Format

### 2.1 Single-item success envelope

All JSON success responses use the following shape unless the endpoint specifies `204 No Content` or a binary file response.

    {
      "data": {
        "id": "UUID",
        "createdAt": "2026-10-26T12:30:00Z"
      },
      "requestId": "UUID"
    }

The example illustrates the envelope only. Each endpoint defines its own exact `data` fields.

### 2.2 List and pagination envelope

    {
      "data": [],
      "pagination": {
        "limit": 25,
        "nextCursor": null,
        "hasMore": false
      },
      "requestId": "UUID"
    }

- `nextCursor` is an opaque continuation token or `null`.
- `hasMore` is a boolean.
- The backend must not disclose database query details or encode sensitive information in a cursor.
- A cursor is not an authorization token; every subsequent request must repeat authentication and ownership checks.

### 2.3 Error envelope

    {
      "error": {
        "code": "VALIDATION_ERROR",
        "message": "One or more fields are invalid.",
        "fieldErrors": {
          "title": [
            "Title must not exceed 200 characters."
          ]
        }
      },
      "requestId": "UUID"
    }

Contract:

| Field | Type | Rules |
|---|---|---|
| `error.code` | String | Stable machine-readable code |
| `error.message` | String | Safe, user-facing summary |
| `error.fieldErrors` | Object or `null` | Field name to array of safe validation messages |
| `requestId` | String | Correlation identifier |

Error messages must not contain stack traces, SQL statements, provider responses, storage paths, extracted medical text, access tokens, share tokens, or secrets.

### 2.4 HTTP status code matrix

| Status | Use |
|---|---|
| `200 OK` | Successful retrieval, update, or completed operation |
| `201 Created` | Resource or asynchronous operation created |
| `204 No Content` | Successful operation with no response body |
| `400 Bad Request` | Malformed JSON, invalid query syntax, or malformed cursor |
| `401 Unauthorized` | Missing, expired, invalid, or unverifiable authentication credentials |
| `403 Forbidden` | Authenticated caller lacks permission for a known resource or action |
| `404 Not Found` | Resource does not exist or is intentionally concealed to prevent cross-workspace enumeration |
| `409 Conflict` | Idempotency conflict, incompatible state transition, or conflicting current version |
| `422 Unprocessable Entity` | Syntactically valid input that violates field, domain, or cross-field validation |
| `429 Too Many Requests` | Rate limit or quota exceeded |
| `500 Internal Server Error` | Unexpected internal failure; response contains no internal diagnostics |

Additional operational statuses:

- `413 Payload Too Large`: upload exceeds configured limits.
- `415 Unsupported Media Type`: file or request media type is unsupported.
- `502 Bad Gateway`: an upstream provider returned an unusable response.
- `503 Service Unavailable`: a required dependency is unavailable or its circuit breaker is open.
- `504 Gateway Timeout`: an upstream dependency exceeded its timeout.

For a nonexistent or unauthorized medical resource, return `404` where disclosure of its existence could reveal private family information. Use `403` for an authenticated caller who is allowed to know the resource exists but lacks a specific permitted action.

### 2.5 Standard error codes

| Code | HTTP status | Meaning |
|---|---:|---|
| `AUTHENTICATION_REQUIRED` | 401 | Credentials are missing |
| `INVALID_TOKEN` | 401 | Access token is invalid or expired |
| `PERMISSION_DENIED` | 403 | Action is not permitted |
| `RESOURCE_NOT_FOUND` | 404 | Resource is missing or concealed |
| `VALIDATION_ERROR` | 422 | Request fields fail validation |
| `INVALID_REQUEST` | 400 | Malformed request |
| `IDEMPOTENCY_CONFLICT` | 409 | Idempotency key was reused for a different operation |
| `INVALID_STATE_TRANSITION` | 409 | Operation is incompatible with the resource state |
| `UPLOAD_TOO_LARGE` | 413 | File exceeds the upload limit |
| `UNSUPPORTED_FILE_TYPE` | 415 | File type is not allowed |
| `RATE_LIMIT_EXCEEDED` | 429 | Request rate exceeded |
| `QUOTA_EXCEEDED` | 429 | Configured usage or storage quota exceeded |
| `AI_PROVIDER_UNAVAILABLE` | 503 | All approved AI providers are unavailable |
| `AI_PROVIDER_TIMEOUT` | 504 | AI provider timed out |
| `DOCUMENT_PROCESSING_FAILED` | 422 | File could not be processed successfully |
| `SHARE_LINK_EXPIRED` | 404 | Share link expired; public callers receive a non-enumerating response |
| `SHARE_LINK_REVOKED` | 404 | Share link was revoked; public callers receive a non-enumerating response |
| `INTERNAL_ERROR` | 500 | Unexpected internal failure |

## 3. Authentication, Authorization & RBAC Enforcement

### 3.1 Authentication flow

MedLab uses Supabase Auth for email and Google authentication.

1. The user authenticates through the supported Supabase Auth flow.
2. The client obtains the Supabase access token.
3. The client sends the access token as a Bearer token to FastAPI.
4. FastAPI verifies the JWT signature and required claims using the configured Supabase project issuer and signing-key/JWKS configuration.
5. FastAPI derives the caller's user UUID from the verified token subject.
6. The backend authorizes the operation against the relevant workspace and resource.
7. Database access uses the RLS enforcement strategy specified in `DATABASE.md`.

The backend must not trust user identity values supplied in JSON or query parameters.

The frontend must not receive or store the Supabase `service_role` key. Refresh-token handling must follow Supabase Auth's supported secure session mechanism and must not place refresh tokens in application logs or URLs.

### 3.2 Roles and permissions

MedLab has a family workspace owner model. The MVP does not define general family-member login accounts or a collaborative role hierarchy.

| Caller | Permission model |
|---|---|
| Public / anonymous | May resolve an unlisted share link only through the public share-link endpoints and only for selected items while the link is valid |
| Authenticated user | May access their own profile and resources within a workspace they own |
| Resource owner | May create, read, update, archive, restore, share, and delete permitted records in their workspace |
| Platform admin | No routine access to medical document contents; any operational break-glass access must be explicitly authorized and audited |
| Background worker | May execute narrowly scoped internal processing jobs; must not accept a client-provided identity as authorization |

`admin` is an application-level role, not a standard Supabase PostgreSQL role. Do not assume a JWT containing a role-like string grants elevated database access.

### 3.3 Resource ownership checks

For each authenticated request:

- Verify the caller's JWT.
- Load the target resource using its UUID.
- Resolve its owning `workspace_id`.
- Verify that the caller is the `family_workspaces.owner_user_id`.
- Verify that the resource is not deleted or otherwise inaccessible.
- Apply operation-specific validation.
- Execute the operation in a transaction where appropriate.
- Write the required audit event without logging medical content.

For nested resources, authorization must be checked through the complete parent chain. A valid document-version UUID does not prove the caller owns its parent document.

For `medical_measurements`, verify that the workspace, family member, and document version all belong to the same authorized workspace and that the member and source version are consistent.

For `share_link_items`, verify that the selected document version belongs to the same workspace as the share link. A link must never be used to access unselected versions or other workspace resources.

### 3.4 Authorization matrix

| Domain | Public | Authenticated owner | Platform admin | Worker |
|---|---|---|---|---|
| Profile | No | Own profile only | No routine access | No |
| Workspace | No | Own workspace only | Operational metadata only, when authorized | Narrow internal task access |
| Family members | No | Own workspace only | No routine content access | No |
| Documents and versions | No | Own workspace only | No routine content access | Processing access only |
| Extracted text | No | Authorized document access only | No routine content access | Processing access only |
| AI summaries | No | Own workspace only | No routine content access | Generate/update task only |
| Measurements | No | Own workspace only | No routine content access | Extraction task only |
| Share links | Public resolution only | Create, inspect, revoke own workspace links | No routine access | No |
| Audit events | No | Restricted owner-facing history only if surfaced by the product | Operational access subject to audit | Write narrowly scoped events |
| Job records | No | No direct access | Operational metadata only | Process claimed jobs |

All routes must be deny-by-default. Any access not explicitly granted in this document is prohibited.

## 4. Complete Internal Endpoint / Action Inventory

### 4.1 Endpoint conventions

All endpoints in this section are relative to `/api/v1`.

- UUID path parameters must be validated before database access.
- All mutation requests must validate ownership and resource state.
- Database field names map explicitly to public JSON field names.
- Request schemas reject undocumented properties.
- All successful operations that create a resource return its public representation, never a raw database row.
- No endpoint returns `token_hash`, `storage_path`, raw provider credentials, raw database errors, or unrestricted extracted text in a list response.
- The frontend must not bypass the API to perform privileged database mutations.

### 4.2 Authentication

Authentication is provided by Supabase Auth rather than custom FastAPI password endpoints. MedLab does not store passwords or password hashes in its own tables.

| Operation | Method / path | Access | Contract |
|---|---|---|---|
| Register | Supabase Auth SDK sign-up flow | Public | Email/password registration, subject to Supabase Auth configuration and verification policy |
| Sign in | Supabase Auth SDK sign-in flow | Public | Email/password authentication |
| Google sign-in | Supabase Auth SDK OAuth flow | Public | Google OAuth through Supabase Auth |
| Refresh session | Supabase Auth SDK session refresh | Session holder | Uses the supported Supabase refresh mechanism |
| Sign out | Supabase Auth SDK sign-out | Session holder | Invalidates the relevant session through Supabase Auth |
| Password reset request | Supabase Auth SDK password-reset flow | Public | Uses configured Supabase email delivery and redirect URLs |
| Password reset completion | Supabase Auth SDK password-update flow | Valid reset session | Updates credentials through Supabase Auth |

The frontend must use configured redirect URLs and must not accept arbitrary callback URLs from query parameters. Supabase Auth errors must be mapped to safe frontend messages rather than returned verbatim.

### 4.3 Profile and workspace

#### `GET /users/me`

- **Purpose:** Retrieve the authenticated user's MedLab profile.
- **Access:** Authenticated user; own profile only.
- **Request:** No body or query parameters.
- **Success:** `200 OK`.

Response fields:

| Field | Type | Nullable |
|---|---|---|
| `data.id` | UUID string | No |
| `data.displayName` | String, max 120 | Yes |
| `data.createdAt` | ISO 8601 timestamp | No |
| `data.updatedAt` | ISO 8601 timestamp | No |
| `requestId` | UUID string | No |

`id` maps to `profiles.id`; `displayName` maps to `profiles.display_name`.

Expected failures: `401 AUTHENTICATION_REQUIRED`, `401 INVALID_TOKEN`, `500 INTERNAL_ERROR`.

#### `PATCH /users/me`

- **Purpose:** Update the user's profile details.
- **Access:** Authenticated user; own profile only.
- **Request body:**

| Field | Type | Rules |
|---|---|---|
| `displayName` | String or `null` | Optional; maximum 120 characters; trim whitespace; reject an empty value after trimming unless clearing is explicitly supported by the product |

At least one supported field must be supplied. Unknown fields are rejected.

- **Success:** `200 OK`; returns the profile response described above.

Expected failures: `401 INVALID_TOKEN`, `422 VALIDATION_ERROR`, `500 INTERNAL_ERROR`.

#### `GET /workspace`

- **Purpose:** Retrieve the authenticated owner's family workspace.
- **Access:** Authenticated user; workspace owner only.
- **Request:** No body or query parameters.
- **Success:** `200 OK`.

Response fields:

| Field | Type | Nullable |
|---|---|---|
| `data.id` | UUID string | No |
| `data.name` | String, max 120 | No |
| `data.status` | Enum | No |
| `data.createdAt` | ISO 8601 timestamp | No |
| `data.updatedAt` | ISO 8601 timestamp | No |
| `requestId` | UUID string | No |

`status` uses the exact `workspace_status` values defined in `DATABASE.md`: `active`, `deletion_pending`, `deleted`.

Expected failures: `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `500 INTERNAL_ERROR`.

#### `PATCH /workspace`

- **Purpose:** Rename the family workspace.
- **Access:** Resource owner only.
- **Request body:**

| Field | Type | Rules |
|---|---|---|
| `name` | String | Required; 1–120 characters after trimming |

- **Success:** `200 OK`; returns the workspace representation.
- **Expected failures:** `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `422 VALIDATION_ERROR`, `409 INVALID_STATE_TRANSITION`.

The MVP does not expose arbitrary workspace ownership transfers or workspace membership-management endpoints.

### 4.4 Family members

#### `GET /family-members`

- **Purpose:** List family members for the current workspace.
- **Access:** Resource owner only.
- **Query parameters:** `limit`, `cursor`, optional `search`, optional `sortBy`, optional `sortOrder`.
- **Success:** `200 OK`; paginated response.

Member response fields:

| Field | Type | Nullable |
|---|---|---|
| `id` | UUID string | No |
| `fullName` | String, max 200 | No |
| `relationship` | Enum | No |
| `dateOfBirth` | `YYYY-MM-DD` | Yes |
| `createdAt` | ISO 8601 timestamp | No |
| `updatedAt` | ISO 8601 timestamp | No |

The database `family_members` schema must use the same documented name-length constraint as the API. If `DATABASE.md` specifies a different maximum for `full_name`, the database limit is authoritative and the API validator must be aligned before implementation.

`relationship` values: `self`, `spouse`, `partner`, `child`, `parent`, `sibling`, `other`.

Only non-deleted members are returned by default.

Expected failures: `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `422 VALIDATION_ERROR`.

#### `POST /family-members`

- **Purpose:** Add a family member.
- **Access:** Resource owner only.
- **Headers:** `Idempotency-Key` required.
- **Request body:**

| Field | Type | Rules |
|---|---|---|
| `fullName` | String | Required; non-empty after trimming; maximum must match `family_members.full_name` |
| `relationship` | Enum | Required; one of the values listed above |
| `dateOfBirth` | Date string or `null` | Optional; valid calendar date; cannot be in the future |

The server derives `workspace_id` from the authenticated owner and sets `created_by_user_id` from the verified token. Clients cannot supply either field.

- **Success:** `201 Created`; returns the member representation.
- **Expected failures:** `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `409 IDEMPOTENCY_CONFLICT`, `422 VALIDATION_ERROR`, `429 RATE_LIMIT_EXCEEDED`.

#### `GET /family-members/{memberId}`

- **Purpose:** Retrieve one family member.
- **Access:** Resource owner only.
- **Success:** `200 OK`; returns the member representation.
- **Expected failures:** `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`.

#### `PATCH /family-members/{memberId}`

- **Purpose:** Update a family member's basic profile.
- **Access:** Resource owner only.
- **Request body:** Any non-empty subset of `fullName`, `relationship`, and `dateOfBirth`, using the creation constraints. `null` is allowed only for `dateOfBirth`.
- **Success:** `200 OK`.
- **Expected failures:** `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `422 VALIDATION_ERROR`, `409 INVALID_STATE_TRANSITION`.

#### `DELETE /family-members/{memberId}`

- **Purpose:** Soft-delete a family member and initiate the applicable record-retention workflow.
- **Access:** Resource owner only.
- **Request:** No body.
- **Success:** `204 No Content`.

This operation must not hard-delete source records or silently orphan medical documents. The service must apply the documented retention and recovery rules to the member's associated records.

Expected failures: `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `409 INVALID_STATE_TRANSITION`.

### 4.5 Medical documents and file versions

#### `GET /documents`

- **Purpose:** List documents for the authenticated owner's workspace.
- **Access:** Resource owner only.
- **Query parameters:**
  - `limit`, `cursor`
  - `memberId`
  - `category`
  - `status`
  - `search`
  - `sortBy`
  - `sortOrder`
- **Success:** `200 OK`; paginated response.

Document response fields:

| Field | Type | Nullable |
|---|---|---|
| `id` | UUID string | No |
| `familyMemberId` | UUID string | No |
| `title` | String, max 200 | No |
| `category` | Enum | No |
| `status` | Enum | No |
| `currentVersionId` | UUID string | Yes |
| `createdAt` | ISO 8601 timestamp | No |
| `updatedAt` | ISO 8601 timestamp | No |

`category` values: `lab_result`, `prescription`, `imaging`, `clinical_note`, `vaccination`, `discharge_summary`, `other`.

`status` values: `uploaded`, `processing`, `ready`, `failed`, `archived`.

The `currentVersionId` is resolved from the current version in `document_versions`; it is not a replacement for the database's version relationship.

List responses must not include extracted text, full summaries, storage paths, file checksums, share tokens, or raw provider metadata.

Expected failures: `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `422 VALIDATION_ERROR`.

#### `POST /documents`

- **Purpose:** Create a medical-document record and start a controlled upload workflow.
- **Access:** Resource owner only.
- **Headers:** `Idempotency-Key` required.
- **Request body:**

| Field | Type | Rules |
|---|---|---|
| `familyMemberId` | UUID string | Required; member must belong to the owner's workspace and be active |
| `title` | String | Required; 1–200 characters after trimming |
| `category` | Enum | Required; one of the documented `document_category` values |
| `fileName` | String | Required; original display filename; maximum 255 characters |
| `mimeType` | String | Required; must match the detected allowed file type |
| `sizeBytes` | Integer | Required; positive and no greater than the configured upload maximum |

The client cannot set `workspaceId`, `uploadedByUserId`, document status, storage bucket, storage path, version number, checksum, or processing status.

- **Success:** `201 Created`.

Response:

    {
      "data": {
        "id": "UUID",
        "familyMemberId": "UUID",
        "title": "Blood test",
        "category": "lab_result",
        "status": "uploaded",
        "upload": {
          "method": "PUT",
          "uploadUrl": "SHORT_LIVED_UPLOAD_URL",
          "expiresAt": "2026-10-26T12:40:00Z"
        },
        "requestId": "UUID"
      }
    }

The upload URL is temporary and scoped to the intended object. It must never be logged or persisted as a public URL. If the chosen storage integration does not support a suitably restricted upload URL, the backend must proxy the upload instead.

Expected failures: `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `409 IDEMPOTENCY_CONFLICT`, `413 UPLOAD_TOO_LARGE`, `415 UNSUPPORTED_FILE_TYPE`, `422 VALIDATION_ERROR`, `429 RATE_LIMIT_EXCEEDED`, `503 SERVICE_UNAVAILABLE`.

#### `POST /documents/{documentId}/complete-upload`

- **Purpose:** Verify an uploaded file and finalize its immutable version record.
- **Access:** Resource owner only.
- **Headers:** `Idempotency-Key` required.
- **Request body:**

| Field | Type | Rules |
|---|---|---|
| `uploadId` | UUID string | Required; must identify the pending upload issued for this document |

The backend derives the actual object path from trusted upload metadata. It must not accept arbitrary storage paths from the client.

- **Success:** `202 Accepted` if verification or processing continues asynchronously; `200 OK` if finalization is complete synchronously.
- **Expected failures:** `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `409 INVALID_STATE_TRANSITION`, `413 UPLOAD_TOO_LARGE`, `415 UNSUPPORTED_FILE_TYPE`, `422 DOCUMENT_PROCESSING_FAILED`.

On successful finalization, the backend records `document_versions` metadata, including `document_id`, `version_number`, `storage_bucket`, `storage_path`, `sha256`, `mime_type`, `size_bytes`, `uploaded_by_user_id`, and `is_current`.

#### `GET /documents/{documentId}`

- **Purpose:** Retrieve a document's metadata.
- **Access:** Resource owner only.
- **Success:** `200 OK`.

Response includes the document-list fields plus:

- `currentVersion`: nullable object with `id`, `versionNumber`, `mimeType`, `sizeBytes`, and `createdAt`.
- `availableSummary`: boolean indicating whether a successful AI summary is available.

Do not return the raw storage path or extracted text.

Expected failures: `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`.

#### `PATCH /documents/{documentId}`

- **Purpose:** Edit document metadata.
- **Access:** Resource owner only.
- **Request body:**

| Field | Type | Rules |
|---|---|---|
| `title` | String | Optional; 1–200 characters after trimming |
| `category` | Enum | Optional; one of the documented category values |

At least one supported field is required.

- **Success:** `200 OK`.
- **Expected failures:** `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `422 VALIDATION_ERROR`, `409 INVALID_STATE_TRANSITION`.

#### `GET /documents/{documentId}/download`

- **Purpose:** Obtain an authorized download for the current document version.
- **Access:** Resource owner only.
- **Query parameters:** `versionId` optional; when supplied, it must belong to the specified document.
- **Success:** `200 OK` with a short-lived download URL and expiry, or a direct file response if the backend is configured to proxy downloads.

Response:

    {
      "data": {
        "downloadUrl": "SHORT_LIVED_DOWNLOAD_URL",
        "expiresAt": "2026-10-26T12:35:00Z",
        "fileName": "blood-test.pdf",
        "mimeType": "application/pdf"
      },
      "requestId": "UUID"
    }

The server must verify the document, version, workspace, and owner before issuing the URL. The signed URL must be short-lived and must not be publicly reusable after expiration.

Expected failures: `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `429 RATE_LIMIT_EXCEEDED`, `503 SERVICE_UNAVAILABLE`.

#### `DELETE /documents/{documentId}`

- **Purpose:** Soft-delete a document and begin recoverable deletion.
- **Access:** Resource owner only.
- **Request:** No body.
- **Success:** `204 No Content`.

The operation must invalidate relevant share links or make their associated items inaccessible immediately. Source files and derived data follow the configured recovery and purge lifecycle.

Expected failures: `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `409 INVALID_STATE_TRANSITION`.

#### `POST /documents/{documentId}/restore`

- **Purpose:** Restore a soft-deleted document during its permitted recovery period.
- **Access:** Resource owner only.
- **Request:** No body.
- **Success:** `200 OK`; returns the document representation.
- **Expected failures:** `401 INVALID_TOKEN`, `404 RESOURCE_NOT_FOUND`, `409 INVALID_STATE_TRANSITION`.

Restore is permitted only while the source and required metadata remain recoverable. It must not silently reinstate expired or revoked share links.

### 4.6 AI summaries and extracted medical information

#### `POST /documents/{documentId}/summaries`

- **Purpose:** Request a plain-English summary and explanation of an uploaded medical document.
- **Access:** Resource owner only.
- **Headers:** `Idempotency-Key` required.
- **Request body:**

| Field | Type | Rules |
|---|---|---|
| `versionId` | UUID string | Required; must belong to the document |
| `regenerate` | Boolean | Optional; default `false` |

The request must not accept a model name, arbitrary system prompt, unrestricted tool list, provider API key, or client-authored instruction that overrides server safety policy.

## 5. Pagination, Filtering, Sorting & Search Conventions

### 5.1 Pagination

All collection endpoints use cursor-based pagination.

| Parameter | Type | Default | Maximum | Rules |
|---|---|---:|---:|---|
| `limit` | Integer | 25 | 100 | Must be between 1 and 100 |
| `cursor` | Opaque string | Omitted | Configured server limit | Must be issued by the API and valid for the endpoint |

The backend must use stable ordering, including a unique tie-breaker such as the resource UUID. A cursor must bind to the relevant ordering and filter context so it cannot be reused to bypass authorization or cause inconsistent pagination.

The API returns:

- `pagination.limit`
- `pagination.nextCursor`
- `pagination.hasMore`

Do not implement unbounded list responses.

### 5.2 Filtering

Only documented filters are accepted:

| Resource | Filter | Validation |
|---|---|---|
| Family members | `search` | Trimmed, bounded text search against the supported name field |
| Documents | `memberId` | Valid UUID owned by the current workspace |
| Documents | `category` | Exact `document_category` value |
| Documents | `status` | Exact `document_status` value |
| Documents | `search` | Bounded text search over document titles and approved metadata |
| Share links | `status` | Computed status such as `active`, `expired`, or `revoked`; not persisted as a new enum |
| Measurements | `testName` | Bounded string matched against the supported test name |
| Measurements | `from`, `to` | Valid ISO 8601 dates or timestamps; `from` must not exceed `to` |

Unsupported filters return `422 VALIDATION_ERROR`. The API must not silently ignore invalid filter values.

### 5.3 Sorting

Supported sort parameters:

- `sortBy`: endpoint-specific allowlist.
- `sortOrder`: `asc` or `desc`.

Default ordering:

| Resource | Default order |
|---|---|
| Family members | `createdAt desc`, then `id desc` |
| Documents | `createdAt desc`, then `id desc` |
| Summaries | `createdAt desc`, then `id desc` |
| Share links | `createdAt desc`, then `id desc` |
| Measurements | `observedAt desc`, with null dates last, then `id desc` |

The backend must map public sort keys to a fixed list of database columns. Client-provided values must never be interpolated into SQL identifiers.

### 5.4 Search behavior

Search must be scoped to the authenticated owner's workspace before matching any data. Search must not cross workspace boundaries or include records in a deleted state unless an explicitly authorized recovery operation is being performed.

The MVP uses PostgreSQL-backed search over supported metadata. Full-text indexing of extracted medical content is not assumed unless explicitly approved and implemented in `DATABASE.md`.

## 6. Streaming, Real-Time & Async Operations

### 6.1 AI generation and asynchronous processing

The MVP uses asynchronous processing with status polling, not an SSE stream.

1. The client calls `POST /documents/{documentId}/summaries`.
2. The backend validates ownership, the requested version, and the idempotency key.
3. The backend creates or reuses a `document_processing_jobs` record.
4. The API returns `202 Accepted` with a `jobId`.
5. A worker extracts the document text, requests a summary through the AI adapter, validates the result, and persists the permitted outputs.
6. The client polls `GET /processing-jobs/{jobId}`.
7. The client retrieves the completed summary through `GET /documents/{documentId}/summaries`.

The frontend should use bounded polling intervals with increasing delay, stop polling on terminal states, and stop when the user leaves the relevant view.

If the client cancels a request or navigates away, this must not be interpreted as proof that the underlying job has been cancelled. Job cancellation is not exposed as a general-purpose endpoint in the MVP.

The worker must implement bounded retries, idempotency, safe failure recording, and protection against concurrent claims of the same job. A failed job must not be reported as successful merely because the provider returned HTTP 200; the returned content must also pass the expected response validation.

### 6.2 File uploads

#### Upload flow

1. Authenticated client requests `POST /documents`.
2. Backend validates metadata and owner permissions.
3. Backend creates a pending document/upload operation and issues a restricted, short-lived upload URL or uses a backend-proxied upload.
4. Client uploads the file to the private storage location.
5. Client calls `POST /documents/{documentId}/complete-upload`.
6. Backend verifies object existence, actual content type, byte size, checksum where supported, and upload ownership.
7. Backend records the immutable version and queues processing.
8. Client polls the job endpoint.

The backend must not trust client-reported MIME type, file extension, or size without verifying the stored object.

#### Allowed file types

The exact file-type allowlist and size limit must be configured centrally and enforced consistently by the API, storage upload policy, and document processor. The MVP supports medical PDFs, scans, and images; the following are the proposed initial allowlist:

- PDF: `application/pdf`
- JPEG: `image/jpeg`
- PNG: `image/png`
- WebP: `image/webp`

SVG, HTML, executable files, archives, and arbitrary office files are not allowed unless the product requirements and security review explicitly approve them.

**Launch-blocking configuration:** The maximum upload size must be defined in the deployment configuration and enforced by the API and storage layer. It must not be assumed from the client's upload metadata. The same applies to maximum image dimensions, request body limits, and any OCR-specific limits.

#### File safety

- Store all medical files in a private bucket.
- Use opaque storage object names rather than names containing patient details.
- Verify file signatures and MIME types.
- Reject zero-byte files and files exceeding configured limits.
- Protect processing against malformed PDFs and image decompression bombs.
- Apply malware scanning where supported by the deployed infrastructure.
- Do not send files to an external AI provider unless the provider adapter and privacy policy explicitly permit the transfer.
- Issue short-lived download URLs only after authorization.
- Do not include raw files, signed URLs, or extracted text in application logs.

### 7.1 Integration inventory

| Service | Purpose and direction | Adapter boundary | Required behavior |
|---|---|---|---|
| Supabase Auth | Authentication; client-to-Supabase and backend token verification | Frontend auth module and backend authentication dependency | Validate issuer, signature, expiry, and subject; never trust client identity fields |
| Supabase PostgreSQL | Persistent application data; backend-to-database | Repository/data-access layer | Enforce ownership, transactions, constraints, and RLS |

| OpenRouter | Outbound AI summary generation | AI provider adapter | Timeouts, bounded retries, output validation, approved fallback only |
| Trusted medical information sources | Outbound source retrieval to ground explanations | Medical-source retrieval adapter | HTTPS, source allowlist/policy, timeouts, citation validation |
| Email delivery | Supabase Auth verification and password-reset messages | Supabase Auth configuration and configured email provider | Use only the provider configured for the project; no second application email service is assumed |

Google sign-in is handled through Supabase Auth's configured Google OAuth integration. The application must not create a second independent Google OAuth token store for the MVP.

No payment provider, billing integration, general-purpose SMS service, or separate analytics service is required by the MVP.

### 7.2 Timeout, retry, and circuit-breaker policy

The following are **initial operational defaults**, not assertions about third-party service guarantees. They must be configurable through environment variables and tuned against measured latency and provider limits.

| Operation | Initial timeout | Retry policy | Failure behavior |
|---|---:|---|---|
| Supabase JWT verification/JWKS retrieval | 3 seconds for network retrieval; cached keys reused | Retry transient network failures with bounded backoff | Reject unverifiable tokens; fail closed |
| Database connection acquisition | 3 seconds | Bounded connection retries | Return `503 SERVICE_UNAVAILABLE` |
| Database query/transaction | 10 seconds default; configurable by operation | Retry only safe transient failures and only when the transaction can be repeated safely | Roll back and return safe error |
| Storage metadata/verification | 10 seconds | Up to 2 retries for transient failures | Keep upload pending or mark processing failure safely |
| Storage signed URL generation | 5 seconds | Up to 2 retries for transient failures | Return `503 SERVICE_UNAVAILABLE` |
| AI provider request | 45 seconds per attempt | Up to 2 retries for transient failures, subject to total job deadline | Fail over to an approved provider if configured |
| Trusted-source retrieval | 8 seconds per source request | Up to 2 retries for transient failures | Continue with other approved sources; clearly indicate when sources could not be retrieved |
| File download proxy, if used | 30 seconds initial connection/read policy, with streaming limits | Do not blindly restart a partially delivered response | Terminate safely; never leak partial data from an unauthorized resource |

Retryable failures include selected network errors, HTTP `408`, `429`, and transient `5xx` responses. Respect `Retry-After` when present and within the job deadline.

Do not retry non-idempotent operations blindly. Database writes must be protected by transactions and idempotency controls. AI generation may incur provider costs even when a client request times out; retry behavior must therefore be bounded and deduplicated.

Use exponential backoff with jitter, for example an initial delay of 500 ms, multiplied by two for each attempt, plus random jitter. Apply a total deadline so nested retries do not exceed the overall operation budget.

### 7.3 Circuit breakers and fallbacks

- Open a circuit after a configurable sequence of consecutive transient failures.
- Keep the circuit open for a configurable cooldown, initially 30 seconds.
- Allow a limited half-open probe after cooldown.
- Do not treat authentication failures, invalid requests, or malformed outputs as ordinary transient network failures.
- When OpenRouter is unavailable, use only a configured, approved fallback provider. Do not dynamically send medical content to an arbitrary provider.
- If no approved AI provider is available, leave the job in a recoverable failed state and return a safe status through the job endpoint.
- If source retrieval fails, do not fabricate citations or claim that live sources were verified.
- If storage or the database is unavailable, do not claim an upload, summary, deletion, or share-link operation succeeded unless its durable state was confirmed.

### 7.4 AI adapter contract

All model calls originate from the backend AI adapter. Frontend code must never call OpenRouter directly with a server API key.

The adapter is responsible for:

- Selecting a configured approved model/provider.
- Applying server-controlled prompts and output constraints.
- Sending only the document data required for the approved task.
- Applying request timeouts and bounded retries.
- Validating provider response shape and content.
- Persisting provider/model identifiers and prompt version in `ai_summaries`.
- Persisting safe failure classifications in `document_processing_jobs.error_code`.
- Preventing raw provider errors, hidden reasoning, or unvalidated content from reaching the frontend.
- Preserving the distinction between extracted source information, general medical explanation, and uncertain interpretation.

AI output must not claim a diagnosis, invent laboratory values, or present a summary as a substitute for professional medical care. When source evidence is unavailable or ambiguous, the output should state that limitation.

### 7.5 Trusted medical sources

Medical-source retrieval must use a backend-controlled allowlist of approved sources and HTTPS endpoints. Sources can include official public health agencies and other sources approved by the product's medical-content policy.

The retrieval adapter must:

- Enforce connection and read timeouts.
- Limit response size and accepted content types.
- Validate returned URLs and citation metadata.
- Prevent arbitrary user-supplied URLs from becoming unrestricted server-side fetches.
- Block private, loopback, link-local, and internal network destinations.
- Avoid executing scripts or following unsafe redirect chains.
- Treat retrieved content as untrusted data, not as instructions for the AI system.
- Store only citation metadata needed to support the generated explanation.
- Never invent a citation when retrieval fails.

The exact source list is a product/security configuration, not a client-controlled request field.

## 8. Webhooks & Inbound Event Verification

### 8.1 MVP webhook inventory

No payment webhook or application-specific third-party webhook is required by the current MVP contract.

Supabase Auth and Storage integrations must use their documented authentication and authorization mechanisms. If an inbound provider webhook is later enabled for asynchronous processing, it must be explicitly added to this document and to the database schema before deployment.

### 8.2 Requirements for any future webhook

Any approved inbound webhook must:

1. Use HTTPS.
2. Validate the provider's documented signature against the **raw request body** before parsing or acting on the payload.
3. Use the exact signature algorithm, timestamp rules, and header names specified by that provider.
4. Compare signatures using a constant-time comparison function.
5. Reject invalid signatures with `401` or `400`, according to the provider contract.
6. Enforce timestamp freshness where supported.
7. Record the provider event identifier durably before processing.
8. Deduplicate repeated event IDs.
9. Process state changes transactionally.
10. Return a success response only after the event is safely accepted for processing.
11. Never log webhook secrets, full signature values, or sensitive payload contents.

### 8.3 Idempotency and replay protection

`DATABASE.md` does not define a dedicated generic webhook-event table. Therefore, no webhook event-deduplication storage is assumed to exist.

If a webhook becomes necessary, add an explicitly reviewed table or equivalent durable idempotency mechanism before implementing the endpoint. Do not reuse `document_processing_jobs.idempotency_key` for unrelated provider events without a documented uniqueness and ownership model.

For current document and AI operations, `Idempotency-Key` must be stored and checked through the relevant internal operation records. Reusing a key with a different payload must return `409 IDEMPOTENCY_CONFLICT`.

## 9. Rate Limiting, Abuse Prevention & Quotas

### 9.1 Initial rate-limit policy

The following limits are initial configurable defaults for deployment, not product entitlements. They must be tuned through testing and monitoring.

| Category | Initial limit | Scope |
|---|---|---|
| Authentication attempts | 5 attempts per minute | IP and provider-supported account protection |
| Password-reset requests | 3 requests per 15 minutes | IP and normalized account identifier |
| Profile and workspace reads | 120 requests per minute | Authenticated user |
| Standard CRUD mutations | 30 requests per minute | Authenticated user |
| Document listing/search | 60 requests per minute | Authenticated user |
| Upload initialization/completion | 10 operations per minute | Authenticated user |
| AI summary generation | 5 requests per minute and 20 per day | Authenticated user, with idempotency enforcement |
| Public share-link resolution | 30 requests per minute | IP and token-hash-derived identifier, with privacy-preserving handling |
| Download URL issuance | 20 requests per minute | Authenticated user or validated share link |

Use a distributed limiter or another deployment-safe shared mechanism if the backend runs multiple instances. In-memory counters alone are insufficient for a horizontally scaled deployment.

Rate-limit keys must not store raw share tokens or authentication tokens. IP-based limits must account for trusted reverse-proxy configuration; do not trust arbitrary client-supplied forwarding headers.

### 9.2 Rate-limit responses

Return `429 Too Many Requests` using the standard error envelope:

    {
      "error": {
        "code": "RATE_LIMIT_EXCEEDED",
        "message": "Too many requests. Please try again later.",
        "fieldErrors": null
      },
      "requestId": "UUID"
    }

Include:

- `Retry-After`: seconds until retry is permitted.
- `X-RateLimit-Remaining`: remaining requests in the applicable window, when available.
- `X-RateLimit-Reset`: UTC epoch timestamp or other single documented format, if implemented consistently.

Do not disclose internal rate-limit keys, other users' activity, or sensitive quota calculations.

### 9.3 Abuse prevention

- Enforce maximum request-body sizes at the reverse proxy and application.
- Validate UUIDs, enums, dates, strings, and array sizes before database operations.
- Apply upload quotas and storage quotas per workspace using configured limits.
- Limit document-processing concurrency and AI provider spend.
- Enforce idempotency on costly operations.
- Apply per-user and per-IP controls to public share links.
- Prevent IDOR by checking workspace ownership on every nested resource.
- Never allow public access to a private storage bucket.
- Avoid resource enumeration by using non-revealing responses for unauthorized resources.
- Protect against SSRF in trusted-source retrieval.
- Treat PDF text, OCR output, uploaded filenames, and retrieved web content as untrusted input.
- Use bounded processing time and memory for documents.
- Make deletion and link revocation effective before background cleanup finishes.

## 10. Data Privacy, Sanitization & Secret Boundaries

### 10.1 Server-only secrets

The following must never cross the client serialization boundary:

- OpenRouter API keys or fallback-provider API keys.
- Supabase `service_role` keys.
- Database credentials.
- JWT signing secrets or private signing keys.
- Email-provider credentials.
- Webhook signing secrets.
- Internal service credentials.
- Raw share-link token hashes.
- Internal prompt templates or private provider request metadata.

Public frontend configuration may contain the Supabase project URL and public/publishable key where required by the Supabase client. These are not substitutes for server-side authorization or RLS.

### 10.2 Sensitive data handling

Medical documents, extracted text, AI summaries, family-member dates of birth, measurements, and share-link contents are sensitive data.

Required controls:

- HTTPS/TLS for all production traffic.
- Private object storage with encryption at rest provided by the selected infrastructure.
- No permanent public file URLs.
- Short-lived signed URLs after authorization.
- Server-side verification of document and workspace ownership.
- Minimal transfer of medical data to external AI providers.
- No medical text in request logs, error messages, analytics, or trace attributes.
- No tokens, signed URLs, or credentials in query-string logs.
- No unrestricted medical data in list endpoints.
- Deletion of derived data according to the source record's retention lifecycle.
- Audit events for sensitive actions, including document access, download, sharing, revocation, deletion, and denied access, as defined in `DATABASE.md`.

The API must not promise end-to-end encryption unless the product implements client-side encryption with the corresponding key-management model. Infrastructure encryption at rest is not equivalent to end-to-end encryption.

### 10.3 Input sanitization and validation

- Trim and validate user-facing text fields.
- Reject invalid enum values and undocumented mutation fields.
- Validate dates, UUIDs, maximum lengths, numeric ranges, and cross-field constraints.
- Escape user-provided text when rendered in HTML.
- Sanitize HTML if the product intentionally accepts rich text; otherwise reject markup in plain-text fields where inappropriate.
- Never render extracted text as trusted HTML.
- Validate MIME type against file signatures.
- Validate external URLs and prevent SSRF.
- Reject unsupported schemes and unapproved redirect destinations.
- Treat AI output as untrusted text until validated and safely rendered.

Sanitization does not replace parameterized database access, authorization, or output encoding.

### 10.4 Output redaction

Never return:

- Database stack traces or SQL errors.
- Database connection strings.
- Authentication or refresh tokens.
- Supabase service-role credentials.
- Share-link token hashes.
- Raw storage object paths.
- Internal provider request/response dumps.
- Raw OCR/extracted text in list endpoints.
- Medical content in error messages.
- Other users' identifiers or private metadata.
- Hidden model reasoning.

When a provider fails, return a stable error code and a safe user-facing message. Put detailed diagnostics in access-controlled operational logs with sensitive fields removed.

### 10.5 Share-link security

- Generate a cryptographically random token with at least 256 bits of entropy.
- Store only the SHA-256 token hash in `share_links.token_hash`.
- Return the raw token only during link creation.
- Verify expiry and revocation on every public access.
- Return only items represented by `share_link_items`.
- Respect `include_summary` and `include_original_file` independently.
- Use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.
- Redact public share tokens from proxy, analytics, and application logs.
- Do not permit a share link to grant access to a workspace or document outside its explicitly selected items.
- Invalidate access when a linked document is deleted or becomes ineligible for sharing.

### 11.6 Email and OAuth configuration

Supabase Auth owns the email and OAuth flows. Configure email delivery, Google OAuth credentials, allowed callback URLs, password-reset redirects, and verification behavior in the Supabase project and its configured provider.

If an external email provider is configured directly in the deployment, its credential must be server-only. Do not invent an additional application email integration if Supabase Auth is already responsible for these messages.

### 11.7 Startup validation

At startup, the backend must validate:

- Required URLs are HTTPS in production.
- Production origins match the approved allowlists.
- Secrets are present when their integrations are enabled.
- Upload and download TTLs are positive and within approved bounds.
- Upload limits and request limits are positive.
- AI retry counts and timeouts are bounded.
- The configured AI provider and model are approved.
- The database is reachable and the schema version is compatible.
- Required migrations have been applied.
- The private storage bucket exists and is not public.
- Rate limiting is backed by a deployment-safe shared mechanism.

The service must fail startup or disable the affected feature safely when critical security configuration is invalid.

**Contract governance:** `API.md` defines the API boundary; `PRD.md` defines approved user-facing scope; `ARCHITECTURE.md` defines deployment and component boundaries; `DATABASE.md` defines the persisted schema and integrity rules. If these documents conflict, do not silently introduce new fields, tables, roles, or endpoints. Resolve the conflict and update the authoritative documents together before implementation.

**MVP release blockers to resolve before production:** confirm the exact upload-size limit, share-link maximum lifetime, deletion recovery/retention duration, final allowed MIME types, production rate-limit values, and the approved AI fallback provider. These settings affect privacy, cost, and operational safety and must not be inferred at runtime.
